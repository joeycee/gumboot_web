Gumboot Flutter Update Summary

Summary of the payment-flow and related product changes already completed in Gumboot Web and Gumboot Backend, so the Flutter app can be updated to match the live product behavior.

Main change: Gumboot now secures the customer payment when an offer is accepted, holds it safely on the platform while the job is active, and only releases it when the customer confirms the work is complete.

1. Payment flow has changed

Old flow:

  1. Worker sends offer.
  2. Owner accepts offer.
  3. Worker finishes job.
  4. Owner is charged on the completion screen.

New flow:

  1. Worker sends offer.
  2. Owner accepts offer.
  3. Owner payment is secured immediately and held by Gumboot.
  4. Worker completes the job.
  5. Owner reviews the work and releases payment.

2. New Flutter accept-offer flow

  1. Owner taps accept.
  2. App checks for a saved card.
  3. App calls POST /api/billing/acceptance-payment-intent.
  4. If a clientSecret is returned, Flutter must complete Stripe confirmation.
  5. Only after payment is secured should Flutter call POST /api/updateJobStatus with job_status = 2.

The offer must not be treated as accepted until both payment hold and status update succeed.

3. New Flutter completion flow

  1. Worker still marks the job completed with job_status = 6.
  2. No card charge happens at that step anymore.
  3. Owner reviews completed work.
  4. Owner taps release payment.
  5. App calls POST /api/billing/release-held-payment.
  6. After release succeeds, app calls POST /api/updateJobStatus with job_status = 7.

4. Backend endpoints to use

New endpoint

POST /api/billing/acceptance-payment-intent

Used before accepting an offer. This secures the owner payment and may return a Stripe clientSecret for Flutter to confirm.

New endpoint

POST /api/billing/release-held-payment

Used when the owner confirms completed work. This releases funds already being held by Gumboot.

Changed behavior

POST /api/updateJobStatus

When accepting an offer with job_status = 2, the backend now refuses the request unless the payment is already secured.

Important

Acceptance is now a two-step flow

Flutter must no longer call updateJobStatus(2) by itself as the whole accept flow.

5. Customer-facing wording already changed

  • On accept: “Your payment will be held securely by Gumboot until the job is completed.”
  • After accept: “Payment secured”
  • While active: “Payment is being held securely”
  • On completion: “Release payment”
  • After release: “Payment released”
  • For workers: “You’ll be paid once the customer confirms the job is complete.”

The Flutter app should match this wording where possible for consistency with web.

6. Cancellation fee support was added

If a job has already been accepted and payment is already being held:

  • If the employer cancels, the employer is refunded minus a NZ$5 cancellation fee.
  • If the worker cancels, the employer gets a full refund and the worker is charged or owes the NZ$5 fee instead.
  • If cancellation happens before payment is held, no cancellation fee applies.
  • If payment was already released, no automatic cancellation fee is applied.

Flutter should show the same cancellation warning copy before confirming cancellation.

7. Supporting UI changes already made on web

  • After an offer is accepted, the owner now sees a quick “Message user” action.
  • The completion review screen no longer shows worker payout numbers in the customer-facing payment breakdown.
  • Payment language across offer review, job details, completion review, and notifications was updated to be simpler and more trust-building.

8. Suggested Flutter implementation checklist

  1. Update offer acceptance to: payment intent -> Stripe confirm if needed -> updateJobStatus(2).
  2. Update completion confirmation to: release-held-payment -> updateJobStatus(7).
  3. Remove any old “charge card on completion” code.
  4. Add missing-card handling before acceptance.
  5. Add cancellation-fee warning text on accepted-job cancellations.
  6. Mirror the updated user-facing wording from web.

9. Testing checklist for Flutter

  • Owner with saved card accepts offer and the offer becomes accepted.
  • Owner without saved card is pushed into card setup before acceptance can finish.
  • Acceptance path works when Stripe requires confirmation.
  • Worker marking completion does not trigger a second charge.
  • Owner releasing payment finishes the job correctly.
  • Duplicate release attempts do not double-pay.
  • Cancellation fee behavior matches employer-cancel and worker-cancel rules.
